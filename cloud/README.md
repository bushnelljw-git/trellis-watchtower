# cloud/: the production Grafana image

This folder is the source of trellis-watchtower's production form: one stateless Grafana on Cloud Run in the TPA app
project, reading Cloud Monitoring for the app, CRM, PHI and call-centre projects, and reached only through IAP on
`watch.${domain}` by `grp-platform`.

**Status: the owner ruled yes on 2026-10-11; the cloud half is tpa-platform's, being built.** The owner's answer to
"Do you want a private monitoring website (watch.<your domain>, behind Google sign-in) showing charts for the whole
system?" was "Yes, everything": charts for the app, the CRM and the call centre, and health numbers (traffic, errors,
uptime) for the member-records area, never member data, through a narrow read-only opening into the protected area.
It reverses tpa-platform D-92 ("No hosted dashboard yet"). This repository holds the image (datasources, dashboards,
the start-up script); tpa-platform builds the cloud side: `sa-watchtower`, the Cloud Run service, the IAP `watch`
host, the perimeter rule and the IAM rows. Nothing here is pushed or deployed from this repository.

as it refuses the other two lists.

**Deploy order, both ways.** An image from before this change ignores `TPA_NOT_DEPLOYED_JOBS` and refuses the
importer's name in `TPA_PAUSED_JOBS`: it does not start, Cloud Run keeps the old revision serving and the apply fails.
This image under a tpa-platform that writes neither list (before its D-181) reads the importer as built: MISSED in red
while it is not built or paused. This image also charts seven counters that must exist before it is deployed, or each
chart is a failed query (Cloud Monitoring's 404 "Cannot find metric(s)"; on beta on 2026-10-25 all seven answered
that): records' `source_sync_alerts` (tpa-platform's D-181) and six the records limit added (its D-180):
`records_velocity`, `records_velocity_settings_changes`, `records_reveals` and `records_staff_member_reads` (PHI
project; Member records' new row) and `auth_stepup_failures` and `auth_admin_revocations` (app project; Sign-in). So,
in order (tpa-platform's infra/README.md, "The order, both ways"):

1. **The records limit's pages step**, that lane's own and run by it before or with its images:
   `-target='module.monitoring_own["phi"]' -target=module.monitoring_app` on beta (tpa-platform's infra/README.md, "The
   records limit"). It makes the six counters (and that lane's four PHI policies and `records_critical`'s filter
   change). Run once tpa-platform's D-181 is on its master, it also carries step 2's first two targets.
2. **tpa-platform's D-181 by resource, in one apply with `image_digests["watchtower"]` at this image's digest:**
   `-target='module.monitoring_own["phi"].google_logging_metric.this["source_sync_alerts"]'`,
   `-target='module.monitoring_app.google_monitoring_alert_policy.catalogue["scheduler-failed"]'` and
   `-target=module.watchtower`. The plan shows exactly three changes: the counter created in the PHI project (none if
   an apply with the importer built already made it); `scheduler-failed` updated in place (its `one_of(...)` gains
   `"feed-ingest-everon-sync"`, its documentation the row 205 sentence); and `module.watchtower[0].google_cloud_run_v2_service.this`
   updated in place (the image's digest, `TPA_NOT_DEPLOYED_JOBS` added, and `TPA_PAUSED_JOBS` gaining the importer only
   while it is built and paused). Anything else in that plan is another change's drift: stop.

While the importer is not built, tpa-platform's change without the digest is safe first on the live image (only
`TPA_NOT_DEPLOYED_JOBS` appears, which it ignores), and this image follows; once the importer is built and paused, only
the apply that moves both works.

The image does not refuse an unset `TPA_NOT_DEPLOYED_JOBS` on beta, though tpa-platform always writes the name: it is
often empty, and whether Cloud Run hands a container an empty value as set has not been checked here, so a refusal
could take the website down exactly while the importer runs. The order is the control.

| Counter | Policy | On the pages |
|---|---|---|
| `sql_automated_backups` (an automated backup's system event audit entry with windowStatus STATUS_SUCCEEDED) | `<db>-backup-missing` (urgent): **today's backup, from 14:00 UTC**, the 09:00 window's four hours and an hour's margin, until the next window: none in 24 hours, with the instance reporting 1,380 of the last 1,440 minutes and never down; held ten minutes, notifying on opening alone | The backups tile shows **a successful backup in the last 30 hours**: ✕ none in 30 h, red, when none came while the instance reported 29 of the 30 hours or more; "no backup yet" (neutral) for one started since. | `database/replication/log_archive_failure_count` | `<db>-pitr-log-archive-failed` (any in 15 minutes) | The tile's failed count in the latest 15 minutes (read as the policy reads it, ALIGN_DELTA over 900 s), red from one, and its status ✕ archive failed, red; a problem row of the area on the overview; per 15 minutes on Databases. |

**Deploy order.** Beta's `sql_automated_backups` counter was made 2026-10-24T19:17Z and counts only from then, so an
image deployed before each instance's first counted backup (about 10:00 to 13:00 UTC on 2026-10-25) shows "✕ none in
30 h" on all four. Build and deploy this image only once each instance's first count is visible in Metrics Explorer;
the same for production-full's first apply of the counter.

**Why two tiles per instance, and not in the area tile.** A stat reads one time range, and Cloud Monitoring returns a
log counter's series only with a point inside it, so a backup a day old cannot be read in the overview's fifteen
minutes. The area tiles and What's wrong now's tables count the failures (each a problem row in 15 minutes); a missing
backup and stalled logs are the two tiles under each database, in the open Databases row and again in What's wrong
now. A database stopped on purpose (`TPA_STOPPED_DATABASES`) reads "database stopped", in no colour.

### Resources: each service's primitives

The owner, 2026-10-13: "Where are all the primitives for each service?" Every Cloud Run service has a **Resources** row,
the same one on its area's page (shut until a viewer opens it, so a page loads only the rows it is asked for) and on its
own page (open) (`resources()` in the generator, one row per service in `SERVICES`):

- **CPU** and **memory**: the p99, p95 and p50 of `container/cpu/utilizations` and `container/memory/utilizations`
  across its instances, each over `run-cpu-high`'s and `run-memory-high`'s own five-minute window and reduced as they
  reduce, so the p99 is the series the policy compares, and the red line at 90% is the line the pager uses;
- **instances**: their **total**, the most in each minute summed over active and idle, exactly as the module's
  `ceiling-<service>` policy reads it (`ALIGN_MAX` over 60 s, `REDUCE_SUM` by service), with that policy's red line
  (above 80% of max_instances rounded up, less a half: 15.5 for 20) where the module writes one, and a grey line at
  max_instances; then active and idle apart. web, ops-web and tpa-api keep Cloud Run's default of 100 (model-gateway
  has 20 and its own `ceiling-model-gateway` since D-249), so the project's regional quota binds first: each project's instances, summed, are drawn against
  `run-instances-near-quota`'s red line (68) and the quota (85);
- **concurrent requests** on the busiest instance (`container/max_request_concurrencies`), with
  `run-concurrency-high`'s red line (71.5) and a grey line at the service's concurrency setting (80; svc-voice's 40 and
  model-gateway's 2, under which that policy never opens);
- **start-up time** (`container/startup_latencies`, a dot per start), **instances billed** (billable instance time per
  second), and **containers killed for memory, crashed or failing to start** (the catalogue's `run_oom_kills`,
  `run_crash_exits` and `run_system_errors`).

**A Cloud Run service has no disk**: what its container writes is held in memory, so its "disk space" is its memory
chart. Each page says so in a note above the rows. Real disk is the databases' (their disk space is drawn in percent
with `<instance>-disk`'s line, and in bytes against the disk's size, on the Databases page and on the area that owns
each) and the buckets'.

**Where each line comes from, and each environment's.** The catalogue's lines (CPU, memory, concurrency, the quota,
Cloud NAT, `<instance>-disk`) are read from the vendored catalogue (`Catalogue.threshold`, with the monitoring
module's defaults for a field a condition leaves out). The rest are tpa-platform's Terraform, written in the
generator with where each comes from: each environment's max_instances, concurrency, instance ceilings and
max_connections (`LIMITS`, from `infra/envs/beta` and `infra/envs/production-full`), and the monitoring module's own
Cloud SQL and ceiling policies (`SQL_POLICIES`, `CEILING_POLICY`, from `infra/modules/monitoring/main.tf`). Every
panel reads its metric as the policy it draws reads it (the module's CPU and memory over five minutes, its
connections over one). One image serves both environments, so a line that differs between them is a number token
`render-dashboards.sh` settles from `TPA_ENVIRONMENT`: production-full keeps records at Cloud Run's default of 100
with no `ceiling-records`, so production draws nothing there where beta draws 15.5 and 20, and its auth-db's
max_connections is 500 where beta's is 100. A service an environment does not build gets no limit line there.

`tests/cloud/test_resources.py` renders the pages for beta and for production and holds every line and every
aggregation to its source: the catalogue, and tpa-platform's Terraform read at the catalogue's pinned commit from the
tpa-platform checkout beside this repository (`TPA_PLATFORM_CHECKOUT` names another), with each root's
`latency_excluded_services`. With no checkout at all those pins are skipped and the run says so; a checkout without
the pinned commit fails them, naming the `git fetch` to run, since a stale checkout would otherwise prove nothing.
Re-vendoring the catalogue moves both together.

**Why a page per service, not one page with a `$service` picker:** a cloud page declares no template variable and
puts no Grafana variable in a query (the rules below), so that no panel takes a viewer's input. Generated
pages keep that rule whole and still give one answer to "where are the primitives for this service": the Services
menu on every page, or the link by the service's title on the overview.

**Thirteen** became **fourteen**: watchtower, this monitoring site (a Cloud Run service in the app project, beta's
`watch.tf`), has its own Resources row on Portal & API, its own page and a tile on the overview, so the site's own CPU,
memory and instances are visible on it. **Fourteen** became **sixteen** with the catalogue at tpa-platform 1e15b0e8:
ops-web, the operations portal's own container (PC-OR-1, on Portal & API), and auth-event-publisher, which sends
sign-in events to records (D-314, on Sign-in). hooks-relay, built only behind its switch and not running, has no page
(`NOT_RUN`).

### How the queries are written

Every query is Cloud Monitoring's **filter form** (Grafana's query "Builder": a metric type, label filters, an
aligner, a reducer, the labels to group by), the same shape as the catalogue's threshold policies. Not PromQL and
not MQL, for what Grafana 12.4 (12.4.11, and 12.4.12 by the image check) actually does (read from the image's own plugin source and checked in the image):

- **PromQL turns a failure into an empty answer.** With the request failing (no credentials), a PromQL query came back
  `200` with an empty frame, where the filter form returned the error with the exact request URL. A PromQL panel that
  fails (a perimeter refusal, a missing role, a broken expression) would read as "no data", or as "0".
- PromQL also needs a leftover `timeSeriesList` block: without one, both the browser and the backend treat the query
  as a legacy query, so the browser drops it and the backend crashes on it.
- MQL is deprecated by Google.

Cloud Run's p95 merges each service's revisions before taking the percentile (`ALIGN_DELTA`, then
`REDUCE_PERCENTILE_95` by service), as `canary-latency` does. A service that holds streams or calls open by design
(web, ops-web and tpa-api the desk's, model-gateway the model's, engine the CRM's ledger stream until Cloud Run's
300 s timeout, svc-voice a call, svc-ops the desk's, watchtower Grafana's long queries and its live tail) has a Cloud
Run p95 that counts each stream's whole life, so each environment's `canary-latency` leaves it out
(`latency_excluded_services`: beta all eight, production-full the engine),
and its page draws `canary-latency`'s 2 s line only where that policy reads it (`LATENCY_LEFT_OUT`, pinned to the
roots). tpa-api's and the engine's own p95 and p50 come from their request lines (`tpa_api_latency`,
`engine_latency`), read as `tpa-api-latency` and `engine-latency` read them (p95 over five minutes, the catalogue's
2 s line), on their area's page and their own; the overview's CRM p95 is crm-web's from Cloud Run and the engine's
from its own line.

What the filter form cannot say is said another way:

- a share of 5xx is shown as counts beside the request counts;
- "error groups in 24 h" is a second aggregation that counts the groups;
- a missed run is each job's successful executions within its own deadline, as a stat that reads MISSED when there
  are none.

**Every query names its project, and the image fills it in at start.** Grafana's Cloud Monitoring datasource drops a
query whose project name is empty, and the ids differ per environment while the image is promoted by digest. So each
query names a placeholder for its datasource's project (`__TPA_PHI_PROJECT_ID__` on `cloud-phi`, and so on).
`render-dashboards.sh` writes the dashboards into `/var/lib/grafana/dashboards` with the service's ids, then starts
Grafana. The lint holds every query to its own datasource's placeholder.

**The rules every cloud dashboard keeps** (`scripts/dashboard_lint.py`; fixtures in `tests/dashboards/cloud-*` and
mutation tests on a real page):

- the filter form on one of the four uids;
- one datasource per panel, so a PHI-project panel reads `cloud-phi` and nothing else;
- monitored resources from the closed list only (`cloud_run_revision`, `cloud_run_job`, `cloudsql_database`,
  `uptime_url`, `cloud_scheduler_job`, `audited_resource`, `servicedirectory_service`, `nat_gateway`, `gcs_bucket`,
  and `gae_app`, the mail check's inbox, read by its counters' own labels alone);
- labels from the closed list only: the catalogue's own, Google's `response_code_class`, `result`, `state`,
  `reason` (why Cloud NAT dropped a packet, on its sent-packet drop counter alone) and `check_id` (which of our uptime
  checks, on uptime results alone: the portal host has three), and the resource labels `service_name`, `job_name`, `database_id`,
  `job_id`, `host`, `gateway_name` (a Cloud NAT gateway) and `bucket_name` (never an object's name). Never a tenant,
  request, session or row id, and never a URL;
- a resource label only with the query's resource type;
- a cross-series reducer, primary and secondary, that is present and not `REDUCE_NONE`, so a query returns only the
  labels it groups by;
- a legend names one allowed label (`${__field.labels.X}`), never the bare `${__field.labels}` map;
- `=` and `=~` filters only;
- no Grafana variable in a query, and no template variable at all, so no dashboard query takes a viewer's input;
- a title that fits its panel on a 1440 px wide screen (8 px a character, the panel's share of the screen less 32 px,
  and 16 px more for a links icon): a title cut to "tpa…" says nothing;
- no panel that reads logs: the datasource has none, and a log-based metric is a metric.

These rules bound what **the dashboards** ask. They do not bound what a viewer can ask: see the next section.

**Against the catalogue** (`tests/cloud/test_catalogue.py`):

- every metric a dashboard queries exists in the vendored `infra/monitoring.yml`, for that datasource's project, as
  beta and production-full name it (beta's CRM counter is `crm_errors`, renamed in the shared app project); a
  Google metric is one a catalogue or monitoring-module policy reads, or one of the few charted beside them to show
  why (`BUILTIN_CONTEXT`: start-up time, billed instances, task attempts, a database's disk bytes, size and I/O,
  Cloud NAT's ports, connections and dropped replies, a bucket's size and object count);
- each metric is read with an aligner that fits its kind;
- every label belongs to its metric or its resource, and never one whose extractor is an unanchored regular
  expression (it could hold a word out of free text). Today that is the CRM's `class` (`"...\nfor Jane Doe"` gives
  `Doe`); tpa-platform is asked to anchor it as the call centre's is. Until then CRM errors are grouped by service only.
  When a vendored catalogue anchors it, the test allows the class and `make cloud-dashboards` puts it back, with no
  code change;
- every service, job, schedule and instance name belongs to that project;
- the job, schedule and instance names agree with the catalogue's own;
- every catalogue metric is charted somewhere.

The catalogue is the copy in `catalogue/`, pinned by sha and checked byte for byte. A metric renamed in tpa-platform
fails this build when its new catalogue is vendored:

```bash
scripts/vendor_catalogue.sh --check ../tpa-platform origin/master   # is the vendored copy current?
make cloud-catalogue                                                # vendor it, regenerate, make lint
make cloud-catalogue CATALOGUE_REF=<branch or sha>                  # another committed ref of ../tpa-platform
```

`make cloud-catalogue` is `scripts/vendor_catalogue.sh ../tpa-platform origin/master`, then `make cloud-dashboards`
and `make lint`: a re-vendor moves the lines read from the catalogue and the Terraform the tests pin
(`tests/cloud/test_resources.py` reads tpa-platform at the pinned commit), so fetch that checkout first.

Edit the dashboards in `scripts/cloud_dashboards.py` and run `make cloud-dashboards`; `make lint` fails a hand edit of
the JSON.

**What a viewer sees when a query fails.** Grafana shows a red triangle on the panel. A panel's "no value" words
("0", "None in this range", "No requests in this range", "not reporting"; next section) are drawn in the neutral
colour, never green, because a counter writes nothing while nothing happens and a failed query shows the same words.
The scheduled-run stats read MISSED in red either way.

- an area's 5xx, error groups and jobs (24 h) tiles, when a database the area reads is stopped (auth-db and tpa-db for

## What a viewer can read

**Any signed-in viewer can ask Cloud Monitoring anything `sa-watchtower` can read**, not only what the dashboards ask.
Explore is off and viewers cannot edit, but a viewer's browser can still post its own query to `/api/ds/query`: any
filter, `REDUCE_NONE` (every label of every series), even another `projectName`. Grafana sends it on as
`sa-watchtower`. `make cloud-image-check` shows this on every run (a signed-in Viewer's query naming another project
with `REDUCE_NONE` reaches Cloud Monitoring), so the day Grafana starts refusing it, the check says so.

**Grafana 12.4 cannot limit a datasource to its saved panels.** I looked (in 12.4.11; the image check shows 12.4.12 still sends a viewer's own query on):

- the image's `defaults.ini` has no such key under `[security]`, `[explore]`, `[query]`, `[dataproxy]` or `[auth]`;
  `[explore] enabled = false` only hides the page;
- the binary's strings have no such feature toggle; the only "dashboard queries" feature validates a dashboard's
  Prometheus queries for compatibility;
- the open-source viewer role holds `datasources:query` on every datasource it can see (`make cloud-image-check`
  prints the permissions). Per-datasource query permissions are Grafana Enterprise's, and would stop the dashboards
  too, since they query the same way.

So the label allowlist, the reducers and the per-project datasources bound the dashboards. **What a viewer can read is
bounded by `sa-watchtower`'s IAM and the perimeter, which tpa-platform's lane sets** (next section):

- the IAP `watch` host under the same access level as `ing-monitoring`, so only the people who may already read the
  PHI project's monitoring reach a page that can;
- `sa-watchtower` holding a custom role with `monitoring.timeSeries.list` alone, not `roles/monitoring.viewer` (which
  also reads alert policies, notification channels, uptime-check configs, dashboards and groups). Viewing the pages
  needs nothing else: a signed-in browser showed no datasource resource call (no `metricDescriptors.list`; that is
  only the query editor's, which viewers do not have). The backend calls only `timeSeries`;
- that role granted on the four TPA projects alone (app, PHI, call centre, and the CRM's where it has one), never on a
  folder or the organisation.

**The residual:** with only that permission, a viewer can still read every metric in those four projects, not just
the catalogue's, and, through the app project's metrics scope, every metric of a project in that scope: the CRM's where
it has one of its own, and the mail check's inbox project (tpa-platform D-400: its two counters and the ten security
counters every project carries; it holds no member data). In particular, Cloud SQL Query Insights' per-query metrics carry normalised query text as a label.
Query Insights is off on tpa-db (tpa-platform's `insights_config`) and on, by default, for auth-db, crm-db and cc-db.
Normalised text replaces values with placeholders, so it should hold no member data; turning it off there too would
close that last path.

## The environment the service sets

None of these is a secret. The image holds no secret at all. Every value is checked at start: a project id must look
like one, the environment is one of the two words, and a paused or stopped name must be one the image knows.

| Variable | Value |
|---|---|
| `WATCH_HOST` | `watch.<domain>` |
| `IAP_AUDIENCE` | `/projects/<project number>/global/backendServices/<bes-watch id>` (a tpa-platform output) |
| `TPA_APP_PROJECT_ID` | the app project's id |
| `TPA_CRM_PROJECT_ID` | the CRM's project; **in beta the app project's id**, because the CRM runs inside the app project (R282) |
| `TPA_PHI_PROJECT_ID` | the PHI project's id |
| `TPA_CC_PROJECT_ID` | beta's call-centre project; empty in production-full, which has none: the Call centre page and every call-centre part of the other pages are left out |
| `TPA_ENVIRONMENT` | `beta` or `production` (tpa-platform's `local.env`): beta's uptime checks pass on IAP's sign-in page, production-full's on the public hosts' `/health`, and the uptime tiles say which; and the limit lines that differ between the two roots (a service's max_instances and ceiling, a database's max_connections) |
| `TPA_PAUSED_JOBS` | comma list of scheduled jobs paused on purpose: tpa-platform fills it from `var.tpa_jobs_paused` (beta's default `nightly-anomalies,accumulator-reconcile`) and, while the administrator-feed importer is built (`feed_ingest_enabled`) and its schedule paused (`feed_ingest_paused`), `feed-ingest-everon-sync` (watch.tf's `local.watch_paused_jobs`). Must be empty with `TPA_ENVIRONMENT=production`: the image refuses to start otherwise |
| `TPA_NOT_DEPLOYED_JOBS` | comma list of scheduled jobs beta builds only behind a switch that is off: tpa-platform writes `feed-ingest-everon-sync` while `feed_ingest_enabled` is false (its default; watch.tf's `local.watch_not_deployed_jobs`), else empty. The image knows that one name alone, refuses a name in this list and `TPA_PAUSED_JOBS` both, and must have it empty with `TPA_ENVIRONMENT=production` |
| `TPA_SIGNIN_ROBOTS` | comma list of what of the sign-in robots tpa-platform has built: `signin-robot-secrets` (their secrets, the secret-read counter and auth's counter of a robot's login tried from elsewhere, from `signin_robot_principals_enabled`), then `synthetics-member-sign-in` and `synthetics-broker-sign-in` (`signin_robots_enabled`; never without the secrets). Unset or empty: none is built, so both robots read "not deployed" and none of their queries is sent (above, "Can people sign in?"). A robot named in `TPA_PAUSED_JOBS` must be named here; must be empty with `TPA_ENVIRONMENT=production` (production-full builds none) |
| `TPA_STOPPED_DATABASES` | comma list of Cloud SQL instances stopped on purpose: tpa-platform fills it from beta's `local.database_stopped` (`join(",", [for db, stopped in local.database_stopped : db if stopped])`; `auth_db` and `auth-db` both work). Must be empty with `TPA_ENVIRONMENT=production`: the image refuses to start otherwise |

Grafana listens on 8080, Cloud Run's default. Its sqlite state is on the container's own disk and is disposable:
there is no Grafana alerting (production alerts are Cloud Monitoring alert policies, owned by tpa-platform's
monitoring module), dashboards and datasources come from files, and users are re-created from the IAP assertion.

## IAP's keys

Grafana verifies IAP's signed assertion against **a pinned copy of Google's IAP key set baked into the image**
(`iap_keys.json`, read through `grafana.ini`'s `jwk_set_file`), never against Google's URL. So the running website
needs no internet path at all: its only one was `www.gstatic.com`, which resolves to Google's front ends, the same
addresses that serve every Google host. tpa-platform's tpa-api pins the same set the same way (its
`tpa_api/iap_keys.json` and `scripts/refresh_iap_keys.py`, R187), and this file keeps that file's shape.

**The trade-off:** when Google rotates IAP's keys and IAP starts signing with a key the pinned copy lacks, every
sign-in to the website fails (401) until the image is rebuilt with refreshed keys and redeployed. Nothing else breaks:
it fails closed. Refreshing regularly keeps that window small: for instance whenever tpa-api's pin is refreshed,
which its own test requires at least every 30 days, and at once if sign-in starts answering 401.

**Refreshing** (from a machine that can reach Google; public keys, never a secret):

1. `scripts/refresh_iap_keys.sh`: fetches Google's set (https to `www.gstatic.com` alone, no redirect), checks every
   key is an ES256 P-256 key, and prints the key ids added and removed. Exit 0: the pin is current; 1: it differs.
   It writes nothing.
2. `scripts/refresh_iap_keys.sh --write`: writes `cloud/iap_keys.json` (with today's `pinned_at`).
3. `make lint` (the key file's tests) and `make cloud-image-check`, then review the diff and commit it.
4. tpa-platform's shared builder builds the new commit; tpa-platform deploys the new digest.

## The image's user and what it writes

tpa-platform's shared image builder (its `cloudbuild/pipeline.py` and `scripts/cloud_build_image.sh`, "Image
pipelines" in its `infra/README.md`) builds and signs this image from a trellis-watchtower commit. Its policy, and how
this image meets it:

- **The user is `10001:10001`**, not the base's `grafana` user (472, in group root): the builder's start check and its
  canonical step refuse any other configured user. The uid has no passwd entry and needs none; `/run.sh` sets `HOME`
  to Grafana's home.
- **It writes exactly two places.** `/var/lib/grafana` (`GF_PATHS_DATA`; `GF_PATHS_PLUGINS` is under it) is
  10001's own, mode 700: the disposable sqlite, the empty plugins folder, and the dashboards `render-dashboards.sh`
  writes at start. `/tmp` keeps the base's 1777 for the render's scratch folder, which is removed before Grafana
  starts. The base's other world-writable folders (`/var/log/grafana`, unused with console logging;
  `/usr/share/grafana/.aws`, unused; `/var/tmp`) are root's and closed. The config, provisioning, baked dashboards
  and entrypoint are root's and read-only.
- **Every base is pinned by digest, and everything fetched by its hash.** The official 12.4.14 image's Go binaries
  (Go 1.26.10) carry `github.com/go-jose/go-jose/v4` v4.1.4, which Container Scanning reports as HIGH (fixed in v4.1.6;
  tpa-platform's build ef0194fb, 2026-10-29, on 12.4.12), and no Grafana 12.x release has the fix. So `grafana`,
  `grafana-server` and `grafana-cli` are rebuilt from Grafana's public v12.4.14 source (BuildKit refuses the tag unless
  it is commit `3c98af3b`) with Go 1.26.10 (the `golang` image), as Grafana's `make build-go` builds them, every module
  checked against Grafana's own `go.sum` and `go.work.sum`, and each binary's module list and build settings must be
  the official one's exactly, but for go-jose's one line (v4.1.6, its go.sum lines pinned in the Dockerfile as
  sum.golang.org lists them). Grafana's official binaries are stamped with its private mirror's commit (`500a5450`),
  these with the public commit they were built from. Everything else in the image (the frontend, the bundled plugins,
  Alpine 3.24.3) is Grafana's. curl and libcurl 8.23.0-r0 (24 findings in build ef0194fb, on 12.4.12's Alpine 3.24.2),
  zlib 1.3.2-r1, musl and musl-utils 1.2.6-r3 and brotli-libs 1.2.1-r0 are what 12.4.14's base already carries; the
  Dockerfile still installs each from Alpine 3.24's own package by its sha256 (no repository, no network; apk checks
  each signature) and requires every installed package of the origins curl, zlib, musl and brotli to be exactly those,
  so a base that falls behind Alpine fails the build here. When a Grafana release carries go-jose v4.1.6, the rebuild
  goes.
- **A shell stays.** The builder's no-shell rule covers tpa-platform's own Python images and `web`, not this one:
  its start check for `watchtower` builds the image, requires the user above, starts it with no network as beta's
  `watch.tf` does, and asks `/api/health` and `/api/search` (401) through `docker exec … wget`, so it needs the
  base's busybox. The entrypoint is a POSIX `sh` script too.
- **`security/scan-exceptions.yaml`** (at this repository's root) is the builder's exceptions file for this image,
  read at the image's own commit, by Container Scanning's package names. It excepts exactly the two fixable HIGH
  findings in `github.com/grafana/tempo`, each until 2026-11-10, when the builder refuses the file until each is
  renewed or removed. No CRITICAL. Both are matched by version alone: Grafana pins Tempo at a main-branch commit of
  2026-04-27 whose pseudo-version (v1.5.1-...) the scanner compares with the fixed 2.x releases, though that commit
  already contains both fixes (and the library serves only the Tempo datasource, which this image never
  provisions). Re-check on the next Grafana release.

## What tpa-platform's lane provides

Filed as a request in [docs/REQUESTS.md §4](../docs/REQUESTS.md#4-the-hosted-dashboards-cloud-half-tpa-platform),
which also asks about Query Insights.

- **No internet path.** The image never fetches IAP's keys ("IAP's keys" above), so the service needs no egress at
  all: not `www.gstatic.com`, and not the subnet rule that allowed it.
- **`sa-watchtower`** with a custom role holding `monitoring.timeSeries.list` alone (not `roles/monitoring.viewer`),
  granted on the app, PHI and call-centre projects (and the CRM project where it has one) and nowhere else. No
  `logging*` role and no invoker. See "What a viewer can read".
- **The perimeter rule** (`ing-watch`): `sa-watchtower` from the watch service to `monitoring.googleapis.com` in the
  PHI project. The PHI project's metrics need it: records, connectors and their jobs (`errors`, `records_*`,
  `connectors_*`, `perimeter_violations`, `monitoring_changes`, `log_metric_changes`, `scheduler_failures`, `run_system_errors`,
  `sql_proxy_errors`), Cloud Run's request, latency, instance, CPU, memory, concurrency, start-up and job metrics for
  them, tpa-db's Cloud SQL metrics, the PHI project's Cloud NAT, and its buckets' size and object count. All of them
  are `monitoring.timeSeries.list` on the PHI project, which the role already holds: the Resources rows ask for no new
  permission. Without the rule every `cloud-phi` panel shows the perimeter's refusal, and nothing else changes.
- **The Cloud Run service** with the environment above, ingress from the internal load balancer only, `min=0`,
  `max=1`, the image by digest, built from a trellis-watchtower commit pinned in `releases/<id>.json`.
  `TPA_PAUSED_JOBS`, `TPA_NOT_DEPLOYED_JOBS` and `TPA_STOPPED_DATABASES` come from the same variables that pause the
  sweeps, build and pause the administrator-feed importer, and stop the databases, so the pages follow each apply.
- **The IAP `watch` host** for `grp-platform`, under the same access level as `ing-monitoring` (its audience goes into
  `IAP_AUDIENCE`), and the IAM rows in the binding inventory.

## Checking it on a laptop

`make cloud-image-check` (`scripts/cloud_image_check.sh`) builds this folder under a throwaway tag, runs it with no
network, checks it, and removes the containers and the image. It never pushes.

0. **The image's configuration.** Its configured user is exactly `10001:10001`, and every `FROM` is pinned by digest
   or is an earlier stage. Grafana's three binaries are Go 1.26.9 builds, and `grafana`'s kin-openapi is v0.149.0 and
   its jsonschema/v6 v6.0.3 (read from each binary's build information); every installed package of the origins zlib,
   musl and brotli is the fixed one.
1. **As it ships, set up as production-full.** Grafana starts and `render-dashboards` writes the production
   pages. Four datasources are inserted and `/api/search` answers 401 without an IAP assertion. Grafana is PID 1, as
   uid 10001 and gid 10001. The baked files are root's and read-only to it, and nothing in the image is writable by
   uid 10001 but `/var/lib/grafana` (700, its own) and `/tmp` (owned, group-owned or world-writable, listed by
   `find`). The image's `grafana.ini` and `iap_keys.json` are the committed ones, the keys are read from the file
   (`jwk_set_file`, no URL), and a token under a pinned key id but signed by another key answers 401.
2. **As beta at rest, signed in as IAP signs people in.** The shipped `grafana.ini` is used unchanged; only the baked
   key file, `/etc/grafana/iap_keys.json`, is replaced by a set holding a throwaway ES256 key, and tokens are signed
   with it. So the shipped config's file path is the one Grafana verifies against, with no network.
   - A wrong audience, a wrong issuer, an expired token and another key's signature all answer 401.
   - The right token signs in a Viewer without `datasources:explore`, and every write answers 403.
   - The dashboards are rendered for beta at rest ("paused", "database stopped", and the importer "not deployed").
   - Every dashboard query reaches Cloud Monitoring's request for its own datasource's project and stops there, at the
     missing Google credentials.
   - A viewer's own query naming another project is sent on too, as "What a viewer can read" says.

By hand:

```bash
tag="trellis-watchtower-cloud:check-$(openssl rand -hex 4)"
docker build -t "$tag" cloud/
docker run --rm -d --name "${tag//[:]/-}" --network none \
  -e WATCH_HOST=watch.example.invalid -e IAP_AUDIENCE=/projects/0/global/backendServices/0 \
  -e TPA_ENVIRONMENT=beta -e TPA_APP_PROJECT_ID=check-tpa-app -e TPA_CRM_PROJECT_ID=check-tpa-app \
  -e TPA_PHI_PROJECT_ID=check-tpa-phi -e TPA_CC_PROJECT_ID=check-callcentre \
  -e TPA_PAUSED_JOBS=nightly-anomalies,accumulator-reconcile -e TPA_NOT_DEPLOYED_JOBS=feed-ingest-everon-sync \
  -e TPA_STOPPED_DATABASES=auth_db,tpa_db "$tag"
docker exec "${tag//[:]/-}" wget -q -S -O /dev/null http://127.0.0.1:8080/api/search   # 401 Unauthorized
docker stop "${tag//[:]/-}"; docker image rm "$tag"
```

Never push it, and never reuse a tag another project uses.

**The builder's own start check**, run against a commit of this repository without touching tpa-platform or sending
anything: unpack the commit where the builder's upload puts it, then run tpa-platform's script on it. It builds by
image id alone and removes the image again.

```bash
up="$(mktemp -d)"; mkdir -p "$up/.sources/trellis-watchtower"
git archive <commit> | tar -x -C "$up/.sources/trellis-watchtower"
bash ../tpa-platform/scripts/image_start_check.sh watchtower "$up"; rm -rf "$up"
```
